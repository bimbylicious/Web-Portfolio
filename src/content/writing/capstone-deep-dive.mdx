## The problem: you can't load-test what doesn't exist yet

Resilience patterns like load balancing, auto-scaling, and failover are usually
things you tune after an incident, against infrastructure that already exists
and already costs money to misconfigure. The capstone started from a narrower
question: could a student, before ever touching a real cloud account, build
enough intuition about cascade failures and capacity planning to make good
decisions once the infrastructure is real? The answer became the Cloud
Resiliency Management Dashboard, a sandbox where you draw a topology, apply
failures and traffic to it, and watch the resilience metrics move.

## Two engines, one interface

The architecture ended up with two simulation engines that coexist in the
same codebase, which was not the original plan.

The first version was backend-driven: an Express API with Prisma/PostgreSQL
and a set of `node-cron` worker jobs, including a system evaluator, a
failover executor, a health checker, an auto-scaler, and a threshold
evaluator, running on a schedule and writing state to a real database. It is
a reasonable architecture, and it is the one that maps most directly onto
how an actual monitoring and orchestration system would be built. For an
interactive teaching tool, though, it was the wrong shape: every simulation
tick meant a network round trip, and iteration speed on the topology canvas
suffered for it.

The active engine now runs client-side. A Zustand store holds all topology
and runtime state in the browser, bridged into the same React Query cache
the app would use for live backend data, so the Dashboard and Resources
pages do not distinguish between numbers that came from a server and
numbers from a simulation tick that happened locally a moment ago.
Simulations run instantly, the canvas stays responsive, and the backend
pipeline still exists, fully preserved and re-enabled via an environment
flag, as documentation of the "real" architecture this sandbox is modeling.

## Modeling capacity, not just uptime

The part of this that is actually queuing theory, rather than just a
topology diagram with red and green nodes, is the load-balancing and
capacity simulation engine. Each node in a topology can be given a
request-type profile, since different request types carry different
service-time characteristics, and the simulation is driven by a
configurable traffic mix rather than a single flat request rate.

That framing matters because most of the interesting failure modes in real
systems are not "the server is down." They are "the server is up but its
effective capacity has collapsed under a traffic mix it was not provisioned
for." Modeling arrival rates against service rates per node, and deriving
utilization from that ratio, is what makes it possible to show why a load
balancer's routing decision helps or does not, not just that latency went
up. It is the same intuition behind Little's Law, the relationship between
concurrency, arrival rate, and time in system. Once utilization approaching
saturation on a specific node is visible, cascade failures stop looking
random and start looking like an obvious next step.

That is the other half of the simulation: pushing a node past capacity and
watching load redistribute onto its neighbors, which, if the topology or the
load balancer configuration was not built to absorb it, pushes those nodes
toward saturation too. The cascade is not scripted. It falls out of the same
capacity model applied node by node.

## Whether it actually worked

The measure of whether any of this succeeded as a teaching tool is not just
whether it ran. It is whether someone unfamiliar with the system could use
it and come away with correct intuitions. User testing put the System
Usability Scale score at 80/100 ("Good" on the SUS grading scale) and the
System Acceptance Questionnaire mean at 5.86/7. The simulation engine, the
Zustand store, topology validation, and the React Query bridge are covered
by 365 automated tests across 16 test files, mainly because a simulator
that is subtly wrong is worse than no simulator at all. If the capacity
math or the cascade logic drifts, every intuition it teaches drifts with it.

## What I would change

Keeping the backend pipeline fully preserved but disabled by default was
the right call for a capstone defense. It is proof the "real" architecture
was built and understood, not just the fast path that shipped. It is dead
weight, though, for anyone extending this outside an academic context. If
this became a real product, the next step would be deciding for real
whether the client-side engine is the permanent architecture, with the
backend rebuilt purely as a persistence and collaboration layer rather than
a simulation authority, or whether the two need to reconverge, running the
same capacity model on both sides so the "documentation" architecture does
not quietly diverge from the one people actually use.
